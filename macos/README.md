# Workbench for macOS

Workbench as a native macOS app: SwiftUI pages, a menu bar item, credentials in the Keychain and
Workbench's own data in SQLite. No Node server and no web view. It needs macOS 26 or later and uses
the Liquid Glass design. Every page is ported from the web version, which it can now replace. The
parity tests compare it with the web version (the launchd service on http://localhost:5180) while
that's still around.

```bash
npm run app:build      # build macos/build/Workbench.app with Xcode
npm run app:install    # build, copy to ~/Applications and open it
npm run app:xcode      # generate Workbench.xcodeproj and open it (⌘R runs, ⌘U tests)
swift test --package-path macos
WORKBENCH_PARITY=1 swift test --package-path macos --filter Parity     # vs the web version on :5180
```

**First run:** open Settings (⌘,) → Data and import the web version's `.env.local`, which fills in
the tokens and preferences, and `data/workbench.sqlite`, which brings over pins, notes, todos and
parked items. Then test each account under Accounts.

Secrets live in one login-keychain item named "Workbench" (a JSON object), so macOS asks once rather
than once per secret, and new secrets go in the same item. Older builds kept one item per secret;
the first launch moves them over and deletes them, which can ask once for each of those.

**Signing.** The Xcode project (`project.yml`, generated by XcodeGen into the git-ignored
`Workbench.xcodeproj`) signs with your Apple Development certificate, so macOS keeps the Keychain
access and other permissions across rebuilds; choose Always Allow once after switching. To get the
certificate: Xcode → Settings → Accounts → your Apple ID → Manage Certificates → + → Apple
Development. `build.sh` then writes its team into `Local.xcconfig` (git-ignored) on the next build.
Without one, builds are signed to run locally and the Keychain asks after each rebuild.
`build-swiftpm.sh` builds without Xcode at all, always signed that way.

**Checking the app without clicking through it:** launch arguments open a page or PR, force light
or dark, and save the window as a PNG, with settings read from a file instead of the Keychain (so
nothing prompts; `-WorkbenchGoogleFrom data/workbench.sqlite` borrows the web version's Google
sign-in). See `DevHooks.swift`:

```bash
open -n macos/build/Workbench.app --args -WorkbenchEnvFile "$PWD/.env.local" \
  -WorkbenchOpen everlab-au/ev-admin#18945 -WorkbenchAppearance dark -WorkbenchSnapshot /tmp/pr.png
```

The snapshot is drawn by the app itself, so it needs no screen-recording permission, but it can't
draw Liquid Glass: glass controls (the toolbar tabs' selection, the PR filter buttons) come out
blank.

## Layout

```
Sources/Workbench/
  WorkbenchApp.swift    scenes (window, Settings, menu bar item), pages, Go menu (⌘1–⌘4)
  ContentView.swift     the pages as toolbar tabs, the Dock badge
  Extras/               app-level state and background refresh (AppState), notifications (Notifier),
                        the global shortcut and open at login (HotKey)
  Theme.swift           the web version's palette: background, text, borders and status tones
  DevHooks.swift        launch arguments for opening a page and saving a snapshot of the window
  SettingsView.swift    accounts, general preferences, data import
  AppSettings.swift     what .env.local held: secrets in the Keychain, the rest in UserDefaults
  Keychain.swift        every secret in one generic password (service com.workbench.app)
  Store.swift           pins, notes, todos, parked, settings: server/store/repo.ts in Swift
  Database.swift        a small wrapper over the system SQLite library
  Integrations.swift    GitHub and Linear GraphQL clients, Linear ticket lookup
  PullRequests/         the Pull Requests page: GitHub queries (GitHubPrs), status rules (Derive),
                        CODEOWNERS, the loader with its caches (PrService), and the views
    Detail/             a PR's details page: queries, timeline and merge readiness (BuildDetail),
                        the Claude hand-off, live checks, and a native Markdown renderer
  Calendar/             Google sign-in and events (GoogleCalendar), meeting sync and the meetings
                        table (Meetings), the Calendar page's grids, and the meeting panels
  Activity/             the Activity page: GitHub events and searches, Linear history, the day
                        builder (BuildActivity), and the Day, Week and Month views
  Today/                the Today page: Linear queries, the rules (BuildToday), pin, note and park
                        controls with posting the park reason, and the sections
Tests/WorkbenchTests/   swift-testing tests; PrParityTests compares with the running web version
Resources/              the asset catalog: app icon and AccentColor
project.yml             XcodeGen spec for the app and test targets; Signing.xcconfig for signing
build.sh                generates the project and builds Workbench.app with xcodebuild
build-swiftpm.sh        the same app with SwiftPM alone, as a fallback
```

The database is `~/Library/Application Support/Workbench/workbench.sqlite`. It uses the same schema
and migrations as `server/store/db.ts`, so a file from either version opens in the other.

## Sharing it

Someone new opens Workbench to a Get started sheet (Help → Get Started brings it back): a GitHub
token is all it needs, with Linear and Google Calendar when they like. Everything is theirs: tokens
go in their Keychain and data in their own `~/Library/Application Support/Workbench`. The home time
zone and the date formats come from their Mac.

**Google Calendar.** `build.sh` bakes Workbench's own Google client into the app from git-ignored
`Secrets.xcconfig` (written from `.env.local`'s `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` the
first time), so nobody makes their own; Settings → Accounts still takes one. For people outside
your Google account to sign in, the client's OAuth consent screen has to be published:
`calendar.readonly` is a sensitive scope, so until Google verifies the app they see an "unverified
app" warning and it's capped at 100 users. An Internal app (Google Workspace) skips both but only
lets in your organisation. A desktop client's secret isn't really secret, which Google expects.

**Handing over the app.** A build signed with an Apple Development certificate runs on your Mac;
on another, Gatekeeper blocks it unless they right-click → Open (or allow it in System Settings →
Privacy & Security). To hand it out without that, sign with a Developer ID Application certificate
(paid Apple Developer Program) and notarize it:

```bash
xcrun notarytool submit Workbench.zip --keychain-profile notary --wait
```

then `xcrun stapler staple Workbench.app`. It needs macOS 26.

## Port plan

Each step ships on its own. Each port keeps the web version's rules (the README at the repo root
describes them), and the TypeScript is the reference.

1. **Foundation** (done): SwiftUI app, Settings with Keychain credentials and import from the web
   version, the SQLite store, GitHub and Linear clients with connection checks.
2. **Signing** (set up; needs your certificate): an Xcode project signed with your Apple
   Development certificate, so the Keychain and later Accessibility permissions survive rebuilds.
3. **Pull Requests list** (done): GitHub search and details, status and merge blockers, CODEOWNERS,
   Linear tickets, the token check, Mine / Reviewing / Team, the waiting-on filters, and parked PRs.
   The page reloads every 30 seconds while it's open. Pin and unpin are in each row's context menu;
   parking with a reason comes with Today.
4. **PR details** (done): double-click a PR (or press Return). The description is rendered as
   native Markdown, with screenshots in a gallery, including private release attachments. Also the
   timeline, threads and change requests, Merge status, the Reviewers, and checks polled every 10s
   while they run (a required check changing reloads the page). Actions are Update branch (after a
   confirm) and Open in Claude for conflicts. Open in Claude finds the repo's clone under Settings →
   General → Local repos, or in ~/everlab, ~/Developer, ~/code, ~/src, ~/Projects and similar
   folders, if its origin matches.
5. **Today** (done): Needs you now (grouped, with nudge targets and team members), Up next, New for
   you with Mark seen (shared with the web version), Focus, Todos, Parked, Deadlines and Waiting on
   others. Every item has pin, note and park; parking can post its reason to Linear and the PRs.
   Meetings arrive with the Calendar port.
6. **Google Calendar** (done): Settings → Accounts → Connect opens Google in your browser, which
   comes back to a one-off listener on 127.0.0.1 (the desktop-app flow Google's Desktop clients
   allow, PKCE-protected). The refresh token goes in the Keychain; one in an imported web database
   is moved there. Meetings sync every minute for the next 30 days, marking rescheduled and
   deleted ones. Calendar shows Day, Week and Month in your home zone or this Mac's; Today shows
   Meetings today and Meeting changes.
7. **Activity** (done): Day, Week and Month in your home zone or this Mac's, from GitHub's events
   feed and searches and Linear's ticket history; stuck and slow flags, linked PRs on the Day
   view's ticket cards, the totals line and Copy summary.
8. **Native extras** (done): your PRs, review requests and calendar refresh in the background, window
   open or not. The Dock badge and the menu bar icon count PRs that need you, and the menu lists
   them. Notifications (each kind switchable in Settings → Notifications) cover PRs that newly
   need you or are ready to merge, review requests, meetings five minutes before (with Join), and
   moved or deleted meetings; what's there the first time is noted silently. Open at login and a
   global shortcut (⌃⌥⌘W, changeable) are in Settings → General. Turn on open at login from the
   installed copy (`npm run app:install`), since it registers the app where it runs.
9. **Productivity**: app usage tracking (`NSWorkspace`, idle and lock), breaks, focus stats.

With step 7 done, the web version (`server/`, `src/`, `shared/`) and the launchd service can go
once you're happy with the app; the parity tests need the web version running, so they'd go too.
